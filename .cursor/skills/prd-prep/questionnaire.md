# Опросник PRD (X-Com)

Задавай вопросы **по блокам**, по 3–5 за раунд. Отмечай ответы пользователя в рабочей памяти/чеклисте скилла.

Формат удобного ответа пользователю в каждом раунде:

```text
Блок C — Цели (2/4)
Ответьте кратко; можно пунктами.

1. ...
2. ...
3. ...
```

---

## A. Паспорт и краткое резюме

1. Как называется инициатива / продукт / изменение?
2. Кто владелец PRD (один человек)?
3. Кто принимает решения, кто консультирует, кого только информируем?
4. Статус документа: черновик / согласование / реализация / завершено?
5. Версия и дата?
6. Тип: новый продукт / развитие / внутренняя система / интеграция / AI-фича?
7. Платформы целевой версии (web / desktop / mobile / другое)?
8. Языки интерфейса?
9. Связанные документы (BRD, исследования, Figma, Scope Matrix, Decision Log, ТЗ)?
10. Резюме в 3–5 предложениях: проблема → решение → ожидаемый результат *(можно собрать в конце из ответов и подтвердить)*.

**Закрыто, когда:** есть название, владелец, статус, тип, платформа, список согласующих (или «только владелец»).

---

## B. Контекст и формулировка проблемы

1. Как работа выглядит сейчас (as-is)?
2. Кто страдает от проблемы (роль/сегмент)?
3. В каком контексте возникает проблема (когда)?
4. Какие боли топ-3…7?
5. Какие есть данные/исследования/обращения/метрики, подтверждающие проблему?
6. Что факт, а что гипотеза?
7. Что будет, если ничего не менять (последствия бездействия)?
8. Почему это приоритет сейчас?
9. Какие ограничения текущей системы/процесса уже известны?

**Проблема одним абзацем (шаблон):**  
«Когда [роль] в ситуации [контекст], возникает [препятствие], из-за чего [последствие].»

**Закрыто, когда:** есть as-is, проблема-абзац, боли, разметка факт/гипотеза, последствия бездействия.

---

## C. Цели, результаты и не-цели

1. Бизнес-цели: что должно измениться для компании (с горизонтом)?
2. Пользовательские результаты: что пользователь сможет сделать иначе?
3. Операционные/процессные цели (время, ошибки, стоимость операции) — если релевантно?
4. Для каждой цели: база → цель → период → способ измерения (или TBD + владелец)?
5. Что **сознательно не** входит в текущую версию (не-цели)?
6. Какую продуктовую гипотезу проверяем этой версией?

**Закрыто, когда:** ≥1 бизнес-цель, ≥1 пользовательский результат, список не-целей, гипотеза (или явное «без гипотезы — compliance/обязательный процесс»).

---

## D. Пользователи, роли и условия использования

1. Сегменты пользователей и их главная потребность?
2. Jobs to be Done / ключевые задачи?
3. Роли в системе и права доступа (RBAC кратко)?
4. Условия использования: устройство, онлайн/офлайн, частота, длительность сессии?
5. Особые ограничения UX/поведения продукта (принципы)?

**Закрыто, когда:** есть роли (хотя бы одна), сегменты или JTBD, условия использования.

---

## E. Основные сценарии

Для **каждого** ключевого сценария:

1. Название и приоритет (Must/Should)?
2. Триггер (кто и что запускает)?
3. Шаги (пользователь + система)?
4. Успешный результат?
5. Исключения / ошибки / пустые состояния / отмены?
6. Какие данные нужны на входе и что сохраняется на выходе?

Собери минимум:
- 1 основной end-to-end сценарий первой версии
- Критичные исключения к нему
- Для AI-фич — сценарий ошибочного ответа модели и действия человека

**Закрыто, когда:** ≥1 сценарий полностью (триггер → шаги → результат → исключения).

---

## F. Объём (MoSCoW)

1. Must: без чего нельзя проверить гипотезу / выполнить основной сценарий / безопасно пилотировать?
2. Should: сильно усиливает ценность, но есть обходной путь?
3. Could: желательно позже?
4. Won't: совпадает с не-целями?
5. Почему каждый Must обязателен (одно предложение обоснования)?
6. Есть ли жёсткий срок/событие, влияющее на объём?

**Правило:** если почти всё Must — вернись к приоритизации с пользователем.

**Закрыто, когда:** четыре корзины заполнены (Won't может ссылаться на не-цели), Must обоснован.

---

## G. Функциональные требования

Для групп по сценарию/объекту:

1. Кто (роль) может сделать что, при каком условии?
2. Успешный результат и сообщение/состояние UI на ошибке?
3. Приоритет (P0/Must …) и источник (цель / сценарий / риск / правило / решение)?
4. Критерии приёмки (наблюдаемое поведение)?
5. Зависимости от других FR/интеграций?

Требование должно быть: понятным, необходимым, однозначным, согласованным, реализуемым, проверяемым, трассируемым, атомарным.

Плохо: «Система должна обеспечивать удобный поиск.»  
Хорошо: «Авторизованный автор может найти сущность проекта по названию; результаты показываются ≤2 с при N сущностях.»

**Закрыто, когда:** все Must-сценарии покрыты проверяемыми FR (или явно вынесены в User Stories со ссылкой, но ключевые FR в PRD есть).

---

## H. Нефункциональные требования

Спроси только релевантное; остальное `N/A`:

1. Производительность: критические операции, нагрузка, целевое время, условия измерения?
2. Доступность: допустимый простой, RTO/RPO?
3. Безопасность: категории данных, auth, шифрование, аудит, хранение/удаление?
4. Совместимость: браузеры, ОС, размеры экрана, полный vs limited mobile?
5. Локализация/a11y?
6. Сопровождаемость: мониторинг, логи, бэкапы, обновления справочников?

**Закрыто, когда:** для выбранной платформы зафиксированы perf + security + devices (числа или TBD с владельцем).

---

## I. Данные, аналитика и интеграции

1. Какие сущности/данные создаёт продукт? Кто владелец данных?
2. Какие события аналитики нужны для метрик успеха?
3. Внешние системы: зачем обмен, направление, критичность, поведение при недоступности?
4. Миграция данных с предыдущего решения — нужна ли?
5. Для AI: источники контекста, что нельзя отправлять, политика PII?

**Закрыто, когда:** список сущностей или ссылка на модель; интеграции перечислены или N/A; аналитика связана с метриками.

---

## J. Ограничения, допущения, риски, открытые вопросы

1. Ограничения: срок, бюджет, стек, инфраструктура, compliance?
2. Допущения (неподтверждённые)?
3. Риски: вероятность, влияние, митигация, владелец?
4. Открытые вопросы: вопрос, владелец, срок?

**Закрыто, когда:** таблицы ограничений/допущений заполнены (могут быть короткими); риски и вопросы не пустые «на всякий случай» без содержания — либо явные пункты, либо «рисков не выявлено на этапе discovery» с датой пересмотра.

---

## K. Метрики успеха и критерии приёмки

1. Продуктовые метрики: база / цель / период / источник данных?
2. Критерии приёмки релиза/пилота (go / no-go)?
3. Как поймём, что гипотеза подтверждена или опровергнута?

**Закрыто, когда:** ≥1 метрика успеха (или TBD) + AC на Must-сценарии согласованы.

---

## L. План запуска и связанные материалы

1. Этапы: пилот → расширение → GA?
2. Кто в пилоте и сколько пользователей?
3. Поддержка, обучение, коммуникации?
4. Мониторинг и план отката?
5. Ссылки на исследования, прототипы, схемы, ТЗ, матрицу scope?
6. История изменений: что уже менялось и почему?

**Закрыто, когда:** есть хотя бы черновой план запуска (или «только внутренний dogfood») и список связанных материалов.

---

## Быстрые добивающие вопросы (если застряли)

- «Что должно быть правдой через 90 дней, чтобы мы сказали „сработало“?»
- «Если можем сделать только одно — что это?»
- «Какой сценарий разочарует пользователя сильнее всего, если сломается?»
- «Какое решение уже принято и не обсуждается?»
- «Где мы гадаем, а где у нас доказательства?»
