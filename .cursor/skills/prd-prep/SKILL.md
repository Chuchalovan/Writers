# PRD Prep (X-Com practices)

Источник методики: [X-Com — Что такое PRD](https://www.xcom.ru/blog/tekhnologii/chto-takoe-prd-product-requirements-document/).

Цель скилла — **не заполнять шаблон наугад**, а через вопросы собрать достаточно ответов, затем собрать PRD. Документ пишется только после закрытия чеклиста (или явного решения пользователя оставить пункт как открытый вопрос с владельцем и сроком).

## Когда применять

- Новый PRD с нуля
- Пересборка/реструктуризация существующего PRD под X-Com
- Пользователь просит «задавай вопросы и собери PRD»

## Жёсткие правила

1. **Сначала вопросы, потом документ.** Не генерируй полный PRD в первом ответе, если данных не хватает.
2. **Один раунд = 3–5 вопросов**, сгруппированных по текущему блоку. Не вываливай весь опросник сразу.
3. После каждого ответа пользователя **обновляй прогресс** (чеклист ниже) и переходи к следующему незакрытому блоку.
4. Отделяй **Факт** / **Гипотеза** / **Решение**. Если пользователь не указал источник — спроси.
5. Запрещены субъективные слова без уточнения: «быстро», «удобно», «интуитивно», «качественно», «просто», «корректно», «при необходимости».
6. PRD отвечает на **что и зачем**, не на детальное **как** (это ТЗ / technical). Не превращай PRD в ТЗ.
7. Если раздел не снижает неопределённость проекта — пометь `N/A` с кратким обоснованием (не копируй шаблон механически).
8. По умолчанию сохраняй результат в `docs/prd/PRD.md` (или путь, который указал пользователь). При обновлении существующего — сохрани архивную ссылку/версию в паспорте.

## Режим работы

### Шаг 0. Старт

Кратко объясни процесс (1–2 предложения) и спроси:

1. Тип инициативы: новый продукт / развитие существующего / корпоративная система / интеграция / AI-функция / другое
2. Есть ли уже BRD, исследования, прототипы, Decision Log, Scope Matrix?
3. Куда сохранить PRD и какой язык документа (ru по умолчанию)?
4. Владелец документа и статус: черновик / согласование / реализация / завершено

Затем читай детальный опросник: [questionnaire.md](questionnaire.md).

### Шаг 1. Интервью по блокам (обязательный порядок)

Иди строго по порядку X-Com. Не перескакивай к FR, пока не закрыты проблема, цели и сценарии.

| # | Блок | Минимум для «закрыто» |
|---|------|------------------------|
| A | Паспорт и резюме | Название, владелец, участники, статус, версия, 3–5 предложений резюме |
| B | Контекст и проблема | Ситуация, аудитория, боль, последствия, факт/гипотеза |
| C | Цели и не-цели | Бизнес + пользовательские результаты + не-цели текущей версии |
| D | Пользователи и роли | Сегменты/роли, задачи, права, условия использования |
| E | Сценарии | ≥1 основной happy path: триггер → шаги → результат → исключения |
| F | Объём | Must / Should / Could / Won't (MoSCoW) с обоснованием Must |
| G | Функциональные требования | Проверяемые FR, связанные со сценариями |
| H | Нефункциональные требования | Хотя бы релевантные: perf / security / availability / devices |
| I | Данные, аналитика, интеграции | Источники данных, события, внешние системы или явный N/A |
| J | Ограничения, допущения, риски, вопросы | Таблицы с владельцами |
| K | Метрики и приёмка | База/цель/период/источник + AC ключевых сценариев |
| L | Запуск и связанные материалы | Пилот/релиз, мониторинг, откат, ссылки, история изменений |

После каждого раунда показывай компактный прогресс:

```text
PRD progress:
[x] A Паспорт
[x] B Проблема
[~] C Цели (не-цели не заданы)
[ ] D Пользователи
...
```

Легенда: `[x]` закрыто · `[~]` частично · `[ ]` не начато · `[-]` N/A

### Шаг 2. Уточняющие петли

Если ответ размытый:

- Переформулируй одним уточняющим вопросом
- Предложи 2–3 варианта ответа на выбор
- Для метрик и NFR требуй числа или явное «TBD + владелец + срок»

Если пользователь говорит «не знаю»:

- Зафиксируй в **Открытые вопросы** (вопрос, владелец, срок)
- Не блокируй весь документ одним TBD, но **не закрывай блок**, пока критичные Must/гипотеза/метрика не решены или явно отложены

### Шаг 3. Сборка документа

Когда все блоки `[x]` или `[-]`:

1. Собери PRD по шаблону [template.md](template.md)
2. Прогони quality gate (ниже)
3. Покажи краткое summary + список оставшихся открытых вопросов
4. Запиши файл

Не пиши полный PRD «наполовину заполненный шаблон» без согласия пользователя. Допустимо промежуточное: «черновик по закрытым блокам A–E» — только если пользователь явно попросил.

## Quality gate (перед финализацией)

- [ ] Проблема отделена от решения
- [ ] Есть измеримые цели (или TBD с владельцем)
- [ ] Не-цели зафиксированы
- [ ] Есть хотя бы один полный сценарий с исключениями
- [ ] Must ограничен; не всё «высокий приоритет»
- [ ] FR однозначны, атомарны, проверяемы, трассируемы к цели/сценарию
- [ ] Нет противоречий между FR/NFR/объёмом
- [ ] Риски и открытые вопросы не скрыты
- [ ] Метрики или явный план измерения после запуска
- [ ] Факты и гипотезы размечены

Если gate не пройден — вернись к вопросам по провалившимся пунктам.

## Анти-паттерны (из X-Com) — не допускай

1. Начинать с пустого шаблона без исследования/вопросов
2. Описывать только идеальный путь
3. Не разделять факт и гипотезу
4. Ставить всем пунктам высокий приоритет
5. Игнорировать эксплуатацию после запуска
6. Забывать миграцию/перенос данных (если есть текущая система)
7. Не фиксировать не-цели
8. Прятать открытые вопросы
9. Писать документ понятный только одной роли
10. Не обновлять PRD после принятых решений

## Адаптация по типу проекта

| Тип | Акцент в вопросах |
|-----|-------------------|
| Новый цифровой продукт | Гипотеза ценности, пилот, метрики обучения, минимум Must |
| Развитие существующего | Текущие метрики, совместимость, миграция, влияние на старые сценарии |
| Корпоративная система | Процессы, роли, правила, аудит, справочники, обязательность использования |
| Интеграция | Сценарий обмена, владельцы данных, SLA актуальности, поведение при недоступности |
| AI-функция | Допустимое качество, источники контекста, human-in-the-loop, оценка ошибок, безопасность данных |

## Связь с артефактами репозитория

При наличии ссылайся и не дублируй SoT:

- BRD → бизнес-цели и эффект
- MVP Scope Matrix → приоритеты релиза при расхождении
- Decision Log → зафиксированные решения
- TZ / technical → детали реализации
- User Stories → детальные AC по задачам

В паспорте PRD укажи правило: **что/зачем = PRD**; **как = ТЗ/technical**; **scope релиза = Scope Matrix** (если есть).

## Стиль общения в интервью

- По-русски, коротко, по делу
- Каждый раунд: 1 строка статуса + 3–5 вопросов + при необходимости «можно отвечать списком»
- Не читай лекцию про PRD, если пользователь не просил
- Верbatim формулировки пользователя в целях/проблеме сохраняй, если они уже точные
